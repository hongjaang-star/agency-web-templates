# 템플릿 유형·변형 관리

한 업종에 여러 유형의 템플릿이 쌓인다(예: 세무사무소 trust · almanac). 이 문서는 무엇을 새 업종으로, 무엇을 새 변형으로 볼지, 그리고 변형을 어디에 어떻게 기록하는지 정한다.
근거: 01 설계(명명 규칙, 변형은 콘셉트 이름), 02 운영(업종마다 변형 2개 이상, 금요일은 변형), 06 마케팅(변형 비교 콘텐츠), decisions.md(시안 3개 → 선택, 사이트 소스 분리).

## 1. 세 단계 구조

| 단계 | 정의 | 위치·이름 | 예 |
|---|---|---|---|
| 업종 (slug) | 고객이 검색하는 업종. 목표와 핵심 섹션이 같다 | `{대분류}-{업종}` | `pro-tax-office` |
| 변형 (variant) | 같은 업종의 다른 디자인 유형. 독립 앱 | `templates/{slug}/{variant}/`, 콘셉트 이름 | `trust`, `almanac` |
| 레벨 (L1~L5) | 기능 복잡도 = 상품 등급. 변형마다 따로 가진다 | `registry/sites.json` 의 `level` | trust L1, almanac L1 |

## 2. 새 업종 · 새 변형 · 같은 변형 수정 판단

| 바뀌는 것 | 결정 | 이유 |
|---|---|---|
| 목표나 핵심 섹션 구성이 절반 이상 다름 (예: 세무사무소 → 세무법인 기업 자문) | **새 업종 slug** | 01 설계의 기준 |
| 디자인 지문(layout·hero·typePair·palette)이나 포지셔닝이 다름 | **새 변형** | 고객에게 "다른 유형"으로 팔 수 있어야 한다 |
| 같은 디자인에 기능만 추가 (상담폼 L2, 예약 L4) | **같은 변형, 레벨 올림** | 디자인이 같으면 다른 상품이 아니다. CHANGELOG 와 `level` 만 갱신 |
| 색·문구·사진만 교체 | 같은 변형 수정 | 납품 커스터마이징 범위 |

## 3. 변형끼리 지켜야 할 차이

- 같은 업종의 변형은 `layout`·`hero`·`typePair`·`palette` 중 **3개 이상**이 기존 변형과 달라야 한다.
- **포지셔닝도 달라야 한다.** 변형마다 `type` 에 "누구에게, 어떤 인상으로"를 한 줄로 적는다. 영업에서 "이런 사무소에는 이 유형"이라고 설명할 수 없으면 변형으로 인정하지 않는다.
- 화면 소스는 공유하지 않는다(`scripts/check-isolation.mjs`). 기존 변형은 `library/` 에서 스타일만 참고한다.
- 업종당 목표는 변형 2개 이상(02 운영). 금요일 작업은 변형이 1개뿐인 업종부터 채운다.

## 4. 변형의 역할과 상태

`registry/sites.json` 항목 하나 = 변형 하나. 아래 필드로 관리한다.

| 필드 | 값 | 의미 |
|---|---|---|
| `status` | `building` · `deployed` · `retired` | retired = 소스 삭제, library 기록만 남음. 배포 목록에서 빠진다 |
| `role` | `flagship` · `alternative` | flagship = 업종 대표(포트폴리오·SNS 첫 노출, 업종당 1개). alternative = 비교·선택지 |
| `type` | 한 줄 포지셔닝 | 예: "지면형 · 설명과 신고 기한을 앞세운 사무소" |
| `legacy` | `true` (선택) | 모노레포·시안 방식 이전에 만든 변형. 다른 업종과 골격이 비슷할 수 있다 |
| `concept` | `concepts/{slug}/{variant}` | 출발한 시안. 이관 변형은 `source` 에 원본 저장소 |

- 새 변형이 들어와도 기존 변형은 지우지 않는다. 대표를 바꿀 때는 `role` 만 바꾼다.
- 지우는 것(`retired`)은 사람이 명시적으로 요청할 때만. 지울 때도 library 기록과 registry 항목은 남긴다.

## 5. 생애 주기

```
시안 3개 (concepts/{slug}/{이름}) ─ 사람 선택 ─▶ building (site/{slug}-{variant} 브랜치)
   │ 선택 안 된 시안: concepts 에 남아 다음 변형 후보        ─ PR 병합 ─▶ deployed
   └──────────────────────────────────────────────────────────────▶ 다음 변형 때 다시 제시
deployed ─ 기능 추가 ─▶ 같은 변형 레벨 업      deployed ─ 사람 요청 ─▶ retired
```

## 6. 변형 추가 절차

1. `/concepts <slug>` — slug 에 이미 변형이 있으면 **변형 추가 모드**: 기존 변형의 지문·포지셔닝을 제외 조건으로 시안 3개를 만들고, 이전에 선택되지 않은 시안도 후보로 함께 제시한다.
2. 사람이 고른다. 기존 미선택 시안을 고르면 그 시안으로 바로 3단계.
3. `/build-site <slug> <concept>` — 완성, `role` 은 기본 `alternative`. 대표 교체는 사람이 정한다.
4. 기록: registry(sites·backlog), library, 관리 시트 한 줄, history.

## 7. 기록 위치

| 어디 | 무엇 | 단위 |
|---|---|---|
| `registry/sites.json` | 원본. 변형별 지문·역할·상태·주소 | 변형 |
| `registry/backlog.json` | 업종 대기열. `variants`(만든 변형), `targetVariants`(목표 수) | 업종 |
| 배포 목록 페이지 | 업종별로 묶어 변형을 나란히. 대표 변형 먼저 | 업종 → 변형 |
| `library/{slug}/{variant}/` | 화면 모듈 캡처·스타일 코드 | 변형 |
| 관리 시트 "템플릿 목록" | 1행 = 1변형. "유형 (포지셔닝)", "역할"(대표 = flagship, 선택지 = alternative) 열. "현황" 탭에 업종 수·변형 2개 이상 업종 | 변형 |

## 8. 영업·마케팅에서 쓰는 법

- 업종 페이지에서 변형을 나란히 보여 주고 "어느 쪽이 우리 사무소다운가" 투표를 받는다(06 마케팅의 변형 비교).
- 문의폼에는 업종과 변형이 자동으로 들어간다. 납품은 고른 변형에서 출발해 고객 로고·사진·말투로 고유화한다(decisions: 데모와 납품 구분).
